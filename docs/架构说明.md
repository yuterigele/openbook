# OpenBook 分层架构说明

本文描述当前代码已实现的运行架构。除明确标记为“兼容”或“待建设”的内容外，均为当前运行路径；不以架构图替代文字说明。

## 1. 总览：六层与主链路

OpenBook 是门店预约 Agent。正式顾客业务链路为：普通微信顾客进入微信客服会话 → 企业微信回调 → 接入与安全检查 → Agent 和预约工具 → MySQL/Redis → 微信客服回复。企业微信好友只负责把顾客引导到客服会话。

系统按以下六层组织：

1. 用户端：普通微信顾客、门店管理员、开发 Web Demo。
2. 接入层：企业微信回调、客服消息同步、HTTP API、会话、回复和多门店路由。
3. 安防层：验签解密、去重、限流、输入保护、可信上下文、认证授权和写入保护。
4. 应用层：Agent、模型、业务工具、定时任务、通知、后台 API 和前端。
5. 数据层：MySQL、Redis、文件会话和容器卷。
6. 观测监控层：日志、指标、Prometheus、Loki、Grafana、飞书告警和可选 CozeLoop tracing。

## 2. 用户端

### 2.1 普通微信顾客

顾客不需要安装企业微信。正式预约入口是门店的**微信客服链接或二维码**（`WECOM_KF_LINK`）。在客服会话中，顾客可以查询师傅和服务、查档期、创建预约、查询本人预约、取消或改约，以及在明确要求时转人工。

### 2.2 企业微信好友：仅获客引导

顾客添加门店员工为企业微信好友时，企业微信推送 `add_external_contact` 事件。接入层使用事件中的 `WelcomeCode` 调用欢迎语接口，发送包含 `WECOM_KF_LINK` 的文字，引导顾客点击后进入微信客服会话。

外部联系人文本消息的 Agent 处理仍存在于代码中，目的是兼容已经配置的旧回调；它不应作为新门店的产品承诺、宣传入口或预约流程。正式说明和门店物料只展示微信客服入口。

### 2.3 门店管理员与平台管理员

商户后台位于 `/admin`，后台 API 由 JWT、角色和权限控制。门店管理员只能访问自己门店；平台管理员可以查看跨门店的运营、审计、套餐和 Agent 观测数据。API Key 可用于受控外部接口访问。后台页面包括预约、师傅、服务、顾客、卡项、请假、通知、数据导出、门店成员和平台管理功能。

### 2.4 本地 Web Demo

`/sessions` 和聊天页面用于开发、演示和测试。它复用 Agent 和会话能力，但不是生产顾客入口。`AGENT_REPLY_MODE=mock` 时，所有企业微信回复仅写入事件记录，不会发送给真实顾客。

## 3. 接入层

### 3.1 HTTP 与企业微信回调

Hertz 提供 Web、后台 API、`/metrics`、企业微信回调和 pprof（按配置）端点。生产部署应通过 HTTPS 反向代理对外暴露企业微信回调；MySQL、Redis、Prometheus、Loki、Grafana 和 pprof 默认仅应在内网或本机可访问。

`/wecom/callback` 的处理顺序如下：

1. 对 URL 验证和消息回调执行企业微信签名校验与 AES 解密。
2. 根据企业主体和 `open_kf_id` 选择门店路由及对应企业微信 Client；单店模式仅在可确定门店时允许兼容路由。
3. 直接回调按消息 ID 做幂等去重；客服事件再通过客服同步接口拉取完整消息。
4. 客服同步 cursor 持久化在数据库。拉取结果过滤非顾客文本和窗口外历史消息，每条 `msgid` 写入持久化已见表，防止重试、重复回调和重启后的重复执行。
5. 同一顾客短时间连续发送多条文本时，按会话 debounce 合并为一次 Agent 请求，降低重复推理和碎片化回复。
6. 会话 ID 使用 `wecom_{shopID}_{externalUserID}`；同一外部联系人联系不同门店时会话隔离。

### 3.2 回复通道

客服回复固定使用微信客服发送接口，按全局串行和 200ms 间隔发送。遇到企业微信“发送频率限制”错误时，按递增退避最多重试 3 次；其他错误（例如会话无效、人工接管、未认证）不走错误的应用消息 fallback，而是记录真实错误。`WECOM_KF_AUTO_TAKEOVER=1` 仅用于允许智能助手接管的账号，在人工工作业场景必须关闭。

外部联系人欢迎语使用 `send_welcome_msg`。欢迎码有时效，因此添加好友事件到达后立即处理；缺少欢迎码时无法补发欢迎语。

### 3.3 后台与本地会话接入

后台 API 注册在 `api/`，路由按 JWT、角色和权限过滤；旧 `ADMIN_TOKEN` 仅作兼容 fallback。Web Demo 会话使用本地 session store，并支持 A2UI 渲染、审批和中止接口，供开发演示使用。

## 4. 安防层

### 4.1 可信身份与租户隔离

用户文本、HTTP body 和模型给出的工具参数均不可信。`shop_id`、外部联系人 ID、会话 ID 和后台操作者身份只从企业微信回调、认证中间件或服务端会话注入 context。工具层必须按门店、顾客身份、预约归属和资源归属校验；模型不能通过参数指定其他门店或其他顾客。

### 4.2 限流与并发保护

进入 Agent 前执行两层令牌桶限流：

- 每顾客：默认每秒 1 条、突发 5 条；key 为 `shopID + customerID`，不同门店彼此独立。
- 单进程全局：默认每秒 100 条、突发 200 条，保护 Agent、模型和下游资源。

被限流的请求立即返回“请求过于频繁，请稍后再试”，不排队也不调用模型。当前没有门店聚合总量限流：同一门店的多个顾客会共享进程全局额度，但没有独立门店 QPS 或每日 token 预算。若需要套餐级配额或多实例一致限流，必须新增 Redis 门店维度令牌桶/计数器，不能依赖当前进程内限流器。

创建预约还受 Redis 时段分布式锁和 MySQL 活跃时段约束双重保护。Redis 健康检查连续 3 次失败时切入只读：查询可用，创建、取消、改约和转人工等写操作被拒绝；连续 3 次成功后恢复写入。

### 4.3 输入保护与内容安全

入口首先执行确定性输入信任评分，拦截提示注入、命令、广告、乱码、异常长文本和预约无关内容，使其不消耗 Agent 或工具。敏感词检查使用本地词表；`SENSITIVE_LLM_FALLBACK=1` 时，关键词未命中可启用无工具权限的模型复核。意图识别先走关键词规则，`SMALL_MODEL_ENABLED` 配置可用时由独立小模型补充模糊分类；小模型没有业务工具权限，失败时退回确定性规则。

### 4.4 认证、授权与数据安全

后台采用 JWT、角色权限和门店范围控制；平台接口要求平台管理员权限。数据库应用账号仅具有业务所需的 `SELECT/INSERT/UPDATE/DELETE` 和迁移权限，初始化由一次性 `db-bootstrap` 容器完成。真实企业微信凭据、模型 Key、数据库密码、JWT 密钥和飞书 Webhook 仅能通过环境变量或密钥管理系统提供，不得提交。

## 5. 应用层

### 5.1 Agent 编排

`internal/agent` 使用 CloudWeGo Eino ADK 构建预约 Agent。每轮注入当前北京时间（`Asia/Shanghai`）、门店上下文、受控历史和当前用户消息。历史消息按数量和字符预算裁剪，超长会话使用非权威摘要；历史不能替代实时工具查询。

Agent 工具白名单包括：敏感检查、意图分类、排班查询、创建预约、取消预约、理发师列表、服务列表、请假查询、本人预约查询、节假日查询和转人工。Agent 不能访问 Shell、文件系统、任意 SQL 或后台接口。单个客户轮次默认上限 60 秒，工具循环最多 8 次。

### 5.2 大模型与降级链

主模型链默认顺序为 **DeepSeek → OpenAI → Ark**，可通过 `OPENBOOK_LLM_CHAIN` 调整。

- **启动阶段降级**：初始化当前 Provider 失败时立即尝试下一个；全部 Provider 都不可用时启动 Stub 模型。Stub 只返回“AI 助手暂不可用”类安全回复，不调用工具、不写库，避免应用整体不可用或误报预约成功。
- **运行阶段降级**：调用期间出现 429、5xx、连接拒绝/重置、EOF 或网络超时等可恢复错误时，当前 Provider 最多重试 2 次；仍失败时按运行时 failover 切到下一个可用 Provider。
- **非可恢复情况**：鉴权错误、配置错误、明显的业务错误不会盲目重试。整轮超时、模型输出不可信或工具结果无法确认时，不写业务数据且不回复操作成功。

全局 usage handler 记录调用次数、错误、Token 和最近 5 分钟 Token；`LLM_DEBUG_LOG=1` 仅输出脱敏并截断后的 prompt/response 日志。配置 `COZELOOP_WORKSPACE_ID` 与 `COZELOOP_API_TOKEN` 时启用 CozeLoop tracing；未配置时不影响业务。

### 5.3 预约与门店业务工具

查询工具读取当前门店的排班、师傅、服务、节假日、请假和顾客本人预约。瞬态连接/超时/数据库锁错误仅对查询类只读工具自动重试 1 次；创建、取消和转人工不会由中间件自动重试，避免重复写入。

创建预约的步骤是：校验姓名、手机号、日期、时间和服务 → 确认师傅归属、营业时间、节假日和请假 → 以顾客手机号、门店、师傅、日期、时间和服务做幂等匹配 → 获取 Redis 时段锁 → MySQL 事务写入 → 提交后重新读取并核验。相同工具调用重复到达时返回既有预约成功结果，不会把已成功预约误回复为“师傅没空”。

取消、查询和改约必须验证当前顾客、门店和预约归属。请假会触发受影响预约处理与通知；爽约、提醒、卡项、服务、客户标签、订阅和连锁门店业务均由确定性服务层处理。

### 5.4 定时任务、通知与人工

应用启动后注册提醒、爽约扫描、续费漏斗、订阅到期、闲时主动推送、理发师请假过期、客服已见消息清理和周报等任务。任务执行结果和最后成功时间进入 cron 指标。通知根据顾客可用身份选择企业微信客服、外部联系人或预留短信/邮件通道；SMTP 未配置时邮件使用 NoopSender，只记录日志。

`handoff_to_human` 当前仅记录审计事件，不会自动创建工单、通知店员或把人工处理结果回推顾客。工单队列、店员通知、状态流转和原会话异步回推属于待建设的人机协作闭环。

### 5.5 后台、静态页和辅助组件

`api/` 提供商户和平台后台 API；`auth/` 提供 JWT、API Key 和权限控制；`static/` 是聊天页和管理端页面，`web/` 提供前端工具与 Vitest 测试。`pool/` 提供有界 worker pool、队列背压和 panic recovery，用于预检查类任务。`mem/` 与 `msgops/` 管理会话、消息构造、转换和历史持久化。`notify/`、`rag/` 和 `evaluation/` 分别承载通知、检索扩展和评估/测试能力；RAG 不在当前预约主链路中强制执行。

## 6. 数据层

### 6.1 MySQL

MySQL 8 是业务事实来源，保存门店、管理员与角色、师傅、服务、顾客、预约、请假、卡项与交易、订阅、事件审计、顾客通知、提醒日志、客服 cursor 和已见消息。预约、客户归属、取消策略和门店隔离由 GORM 事务与条件查询保证。客服 cursor 与 `msgid` 去重均持久化，因此重启不丢去重状态。

### 6.2 Redis

Redis 7 用于预约时段锁和健康保护。锁失效、Redis 不可用或写入结果无法确认时，写操作安全失败；MySQL 活跃时段约束仍是最终并发兜底。当前顾客/全局限流器是进程内实现，不使用 Redis，因此不跨实例共享。

### 6.3 文件与容器卷

本地会话、演示数据和工作区位于应用数据卷；MySQL、Prometheus、Loki 和 Grafana 各有独立 Docker volume。敏感词生产词表可从部署文件加载，缺失时使用空词表并记录日志。`docker compose` 默认只启动 app、MySQL、Redis 和数据库初始化；观测组件需要 `--profile observability` 显式启动。

## 7. 观测监控层

### 7.1 日志、指标和看板

应用输出结构化/带前缀日志，覆盖回调、路由、去重、限流、Agent、工具、模型、Redis、定时任务和企业微信发送失败。`/metrics` 暴露敏感检查、LLM 用量与错误、限流、Agent 与工具调用、Redis 只读、运行时模型切换和 cron 心跳指标。

可观测 profile 中：Prometheus 每 15 秒抓取 `/metrics`；Grafana Alloy 通过只读 Docker Socket 发现 OpenBook 容器并将日志写入 Loki；Grafana 预置 Prometheus 和 Loki 数据源及仪表盘。平台管理员还能在后台查看 Agent 任务、工具成功率和 Token 用量。

工具技术执行 SLO 为**成功率不低于 95%**。正常业务拒绝不计技术失败；`[tool error]` 计失败。累计调用达到 20 次后计算 SLO 状态，`openbook_agent_tool_slo_met=0` 表示未达标。

### 7.2 已配置的 Prometheus 告警

以下规则位于 `observability/prometheus/rules/openbook.yml`：

| 告警 | 条件 | 持续时间 | 级别 |
| --- | --- | --- | --- |
| MetricsTargetDown | OpenBook `/metrics` 连续抓取失败 | 2 分钟 | critical |
| HighLLMErrorRate | 最近 5 分钟 LLM 错误率 >10% | 5 分钟 | warning |
| RateLimitRejections | 最近 5 分钟限流拒绝 >20 | 5 分钟 | warning |
| RedisReadOnly | Redis 只读指标为 1 | 1 分钟 | critical |
| HighLLMFallbackRate | 最近 5 分钟模型运行时降级率 >20% | 5 分钟 | warning |
| HighToolFailureRate | 最近 5 分钟工具失败率 >10% | 5 分钟 | warning |
| FeishuAlertBridgeDown | 飞书告警桥不可用 | 2 分钟 | critical |
| CronTaskFailures | 最近 15 分钟存在 cron 失败 | 1 分钟 | warning |
| CronHeartbeatMissing | reminder 或 leave_expirer 超过 5 分钟未成功 | 2 分钟 | warning |

当前规则文件尚未包含“工具 SLO 未达 95%”的独立 Prometheus 规则；已有指标已暴露，应增加 `openbook_agent_tool_slo_met == 0` 告警后再把它视为可外送通知的正式告警。

### 7.3 飞书通知

配置 `FEISHU_ALERT_WEBHOOK_URL` 后，Redis 初始化失败、切入只读和恢复写入会直接通知飞书；模型降级监控在最近 5 分钟调用不少于 20 次且运行时降级率高于 5% 时通知，活动期间最多每 15 分钟重复一次，恢复后发送恢复通知。Grafana 通用 webhook 可经 `feishu-alert-bridge` 转换并发送到 `FEISHU_GRAFANA_WEBHOOK_URL`。仅启动 Prometheus 规则不会自行对外发通知，必须配置 Grafana Alerting 或对应通知链路。
