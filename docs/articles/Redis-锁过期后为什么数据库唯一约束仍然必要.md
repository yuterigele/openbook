# 已经用了 Redis 锁，为什么还是会重复预约？

> 本文用 OpenBook 预约 Agent 的真实改造过程，讲清楚 Redis 锁和数据库唯一约束各自是干什么的。

假设两个顾客几乎同时给预约 Agent 发消息：

> 我想约 Tony 明天下午 2 点剪发。

系统收到两条消息后，都去查了一遍档期。巧的是，两次查询都发生在预约写入数据库之前，所以它们看到的结果都是：

> 14:00 目前没人预约。

接下来，两个请求都开始创建预约。如果系统没有并发保护，数据库里就可能出现两条 Tony 14:00 的有效预约。

这时模型并没有理解错，Prompt 也没有失效。问题只是：**两个请求同时改了同一份数据。**

## 第一反应：加一把 Redis 锁

最常见的解决办法，是在创建预约前加一把 Redis 锁。

可以把它理解成门口的排队员。

顾客 A 先来，排队员把“Tony、明天、14:00”这个号码牌交给 A。顾客 B 再来时，看到号码牌已经被拿走，只能等一会儿或者换个时间。

代码里的意思差不多：

```go
l, err := lock.AcquireAppointmentLock(
    ctx,
    barber.ID,
    params.Date,
    params.Time,
)
```

拿到锁的请求继续创建预约。没拿到锁的请求不会硬往数据库里写，而是告诉顾客：这个时间刚被别人抢了，要不要换一个时间？

到这里看起来已经解决了。

但问题是，这个“号码牌”会过期。

## Redis 锁为什么要过期

假如一个请求拿到锁以后，服务突然崩了。如果锁永远不过期，这个时段可能永远无法再预约。

所以 Redis 锁通常都会设置有效期。OpenBook 默认是 10 秒。

正常情况下，10 秒足够完成一次数据库操作。但真实系统不总是正常：

- 数据库突然变慢；
- 应用与 Redis 之间短暂断网；
- 服务器 CPU 很忙，请求停顿了一会儿；
- Redis 重启或发生主从切换；
- 后来业务变复杂，写入时间超过了原来的估计。

于是可能出现这种情况：

```text
顾客 A 拿到锁，开始创建预约
        ↓
数据库突然变慢
        ↓
Redis 锁到期
        ↓
顾客 B 拿到同一把锁，也开始创建预约
        ↓
A 和 B 都往数据库里写
```

如果数据库本身没有限制，两条预约还是可能同时成功。

所以 Redis 锁更像“维持排队秩序的人”，而不是最后拍板的人。

## 给锁自动续期，够不够？

为了避免业务还没做完，锁就先到期，OpenBook 给锁加了自动续期。

请求拿到锁以后，后台会定期检查：

> 这把锁还是我的吗？如果是，就再延长一会儿。

释放锁时也会先核对身份，只释放自己的锁，避免 A 把后来属于 B 的锁删掉。

如果自动续期失败，系统会尽量取消正在进行的数据库操作，并告诉顾客：这次操作没有确认成功，请重试。

这已经能挡住大部分问题，但仍然不能保证百分之百安全。

原因并不复杂：网络故障、进程暂停和数据库提交可能刚好挤在同一瞬间。应用以为自己已经取消了操作，数据库却可能刚刚完成提交。以后新增的后台导入功能，也可能忘记走 Redis 锁。

因此，自动续期是在降低出错概率，不是在提供最终保证。

## 最后一道门应该放在数据库

预约最终保存在数据库里。因此“同一时段不能有两条有效预约”这条规则，也应该由数据库守住。

这就像电影院卖座位票：

- Redis 锁负责让买票的人排队；
- 数据库负责保证同一个座位只能卖出一张有效票。

即使排队系统临时出了问题，收银台也不能把同一个座位卖两次。

OpenBook 会给每个有效预约生成一个“时段身份证”。这个身份证由下面四项共同决定：

```text
门店 + 理发师 + 日期 + 时间
```

比如：

```text
人民路店 + Tony + 2026-08-24 + 14:00
```

数据库要求这个身份证不能重复。因此，即使两个请求同时写入，也只能有一个成功。另一个请求会被识别为“时段已被占用”，然后引导顾客换时间。

## 为什么不直接限制“所有历史预约”

还有一个容易踩坑的地方。

假设顾客 A 预约了 14:00，后来取消。顾客 B 再预约同一个 14:00，这是正常业务。

如果数据库简单地规定“Tony + 日期 + 时间永远不能重复”，取消后的时段也无法再次预约。

所以 OpenBook 只给正在生效的预约设置“时段身份证”：

- `active`：有身份证，占用时段；
- `cancelled`：身份证清空，不再占用；
- `completed`：身份证清空；
- `noshow`：身份证清空。

这样既能防止两条有效预约撞在一起，又能完整保留取消和完成记录。

数据库字段大致是这样：

```go
ActiveSlotKey *string `gorm:"uniqueIndex:idx_appointment_active_slot"`
```

有效预约的值不能重复；已经结束的预约使用 `NULL`，可以保留多条历史记录。

## 两层保护分别做什么

现在可以用一句话讲清楚：

> Redis 锁负责让请求排队，数据库唯一约束负责绝不卖出两张相同的票。

Redis 锁的价值是：

- 尽早拦住冲突请求；
- 减少数据库同时写入；
- 让顾客更快得到“换个时间”的回复。

数据库唯一约束的价值是：

- Redis 失效时仍能阻止重复预约；
- 两个应用实例同时写入时仍然有效；
- 后台导入等其他入口忘记加锁时仍有兜底；
- 最终保存的数据一定符合业务规则。

它们不是二选一，也不是重复建设。

## 写进数据库还不算结束

预约系统还有一个危险情况：数据库操作超时了，但应用不知道到底有没有写成功。

这时候最糟糕的处理方式，是让 Agent 猜一个答案，或者马上再创建一次。

OpenBook 的做法是：创建完成后，再从数据库读取一次，检查门店、师傅、日期、时间和状态是否都正确。

只有确认最终记录确实存在，Agent 才能回复“预约成功”。

如果无法确认，就明确告诉顾客操作结果暂时无法确认，让顾客查询预约，而不是编一个成功结果。

这也是做业务 Agent 时很重要的一条原则：

> 模型可以负责把话说得自然，但成功还是失败，必须由真实数据决定。

## 测试也不能只测正常预约

正常创建一条预约，只能证明功能能跑，不能证明并发安全。

OpenBook 还测试了这些情况：

- 同一时段创建第二条有效预约，必须失败；
- 第一条预约取消后，这个时段可以重新预约；
- 已取消和已完成的历史记录可以继续保留；
- 已取消预约想恢复时，如果时段已被别人占用，恢复失败；
- 两个请求同时抢一个时段，最后只能成功一个；
- 老数据已经存在重复时，系统拒绝带着错误数据启动。

最后一项尤其重要。给旧项目补唯一约束时，如果历史数据早已重复，不能假装没看到，更不能随便删掉一条。应该先发现问题，再由业务人员确认怎么处理。

## 一次可靠预约经过哪些步骤

把整个过程翻译成人话，大概是这样：

```text
先确认你是谁、预约哪家店
        ↓
确认师傅上班、时间可约
        ↓
检查是不是同一个请求重复提交
        ↓
用 Redis 锁让同一时段的请求排队
        ↓
写入数据库
        ↓
数据库拒绝第二条相同的有效预约
        ↓
重新读取，确认预约真的成功
        ↓
Agent 才回复顾客
```

每一步都有自己的作用。少了最后的数据库约束，Redis 出问题时可能重复预约；少了 Redis 锁，大量冲突会直接挤进数据库；少了成功后的重新读取，Agent 可能把不确定结果说成成功。

## 最后

Redis 锁很好用，但它不是保险箱里的最后一道锁。

它会过期，会断网，也可能被某条新业务链路绕过。真正不能被破坏的业务规则，应该交给保存最终数据的数据库。

对于预约 Agent 来说，最稳妥的分工是：

> Redis 负责排队，数据库负责守底线，最终查询负责确认结果。

这样即使模型、网络或缓存出现波动，系统也不会因为一句“预约成功”，让两位顾客同时出现在 Tony 的 14:00。
