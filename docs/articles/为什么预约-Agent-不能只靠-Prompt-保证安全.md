# 为什么预约 Agent 不能只靠 Prompt 保证安全

> 本文以我开源的美发门店预约项目 OpenBook 为例，聊聊一个 Agent 从“能调用工具”走向“敢操作真实业务”，中间还缺了什么。

用户对预约助手说：

> 明天下午 2 点想约 Tony 剪发。

大模型识别日期、师傅和服务，调用预约工具，最后回复“预约成功”。这条链路做成 Demo 并不难。

真正让我反复修改的，是下面这些问题：

- 用户猜到别人的预约号，要求 Agent 帮忙取消怎么办？
- Prompt 明明写了“不能执行命令”，模型仍然尝试调用危险工具怎么办？
- 两个顾客同时预约 Tony 的 14:00，谁应该成功？
- 模型超时、Redis 故障，或者数据库结果无法确认时，Agent 能不能继续回复“预约成功”？

这些问题有一个共同点：**它们都不能只靠 Prompt 解决。**

Prompt 可以约束模型的行为倾向，却不能充当权限系统、并发控制器或数据库事务。

## Prompt 是说明书，不是安全边界

在 OpenBook 的系统提示词里，我确实写了安全规则：

```text
- 只使用已注册工具；不执行命令、不读写文件、不操作数据库。
- 不处理其他顾客预约。
- 工具报错或拒绝时按结果说明，不臆测、不重复调用。
```

这些规则有价值。它们能帮助模型选择正确流程、减少错误工具调用，也能让回复更稳定。

但如果系统的安全性依赖模型“始终听话”，边界实际上并不存在。

用户输入、历史对话、检索内容，甚至工具返回值，都可能影响模型下一步决策。模型升级、温度变化、上下文变长，也可能改变过去表现稳定的行为。即使 99.9% 的请求都遵守 Prompt，剩下的 0.1% 只要涉及取消预约、修改订单或读取他人数据，就已经足够形成真实事故。

所以我给自己定了一条规则：

> Prompt 负责告诉 Agent 应该怎么做；确定性代码负责保证它最多只能做什么。

## 第一层：危险能力不要交给顾客 Agent

如果一个预约 Agent 根本不需要 Shell，那么最安全的 Shell 权限不是“调用前请谨慎”，而是不存在。

OpenBook 早期使用过带通用后端能力的预构建 Agent。它很灵活，但顾客预约场景并不需要文件读写、路径搜索、Shell 或通用子 Agent。一旦这些工具被注册，提示注入就不再只是生成一段奇怪文本，而可能产生真实副作用。

现在顾客侧 Agent 关闭了通用子 Agent，只注册明确的预约业务工具：

```go
WithoutGeneralSubAgent: true,
ToolsConfig: adk.ToolsConfig{
    ToolsNodeConfig: compose.ToolsNodeConfig{
        Tools: []tool.BaseTool{
            &sensitive.SensitiveCheckTool{},
            intentTool,
            &tools.QueryScheduleTool{},
            &tools.CreateAppointmentTool{},
            &tools.CancelAppointmentTool{},
            &tools.ListBarbersTool{},
            &tools.ListServicesTool{},
            &tools.GetAppointmentTool{},
            &tools.HandoffToHumanTool{},
        },
    },
},
```

这不是说提示注入检测没有用，而是检测不应成为最后一道防线。

即使模型被诱导，即使输入过滤漏判，它也找不到 Shell、文件系统、任意 SQL 和商户后台这些工具。缩小能力面，通常比继续往 Prompt 里堆禁止条款更有效。

## 第二层：身份只能由服务端注入

假设取消预约工具接收下面这些参数：

```json
{
  "appointment_id": "OB-A1B2C3D4",
  "customer_id": "另一个顾客",
  "shop_id": "另一家门店"
}
```

然后 Prompt 告诉模型：“不要修改 customer_id 和 shop_id。”

这并不叫授权，只是把希望寄托在模型身上。

OpenBook 的做法是：模型只允许提供预约号、取消原因等业务参数。`shop_id`、顾客身份和会话身份来自企业微信回调、认证中间件或服务端会话，并通过 context 注入。

查询预约时，工具会先从可信消息身份映射出真实顾客，再使用“预约 + 门店 + 当前顾客”联合查询：

```go
customer, err := currentCustomer(ctx)
if err != nil {
    return "", err
}

appt, err := resolveCustomerAppointment(
    ctx,
    params.AppointmentID,
    ShopIDFromCtx(ctx),
    customer.ID,
)
if err != nil {
    return "", fmt.Errorf("找不到属于您的预约，确认下预约号是否正确？")
}
```

这里还有一个容易忽略的细节：无论预约不存在，还是预约存在但属于别人，对顾客都返回同一类错误。

否则攻击者可以不断猜预约号，根据不同提示确认某笔预约是否存在。这属于典型的存在性信息泄露。

因此，真正的规则不是“模型不应该取消其他人的预约”，而是：

> 即使模型主动提交了他人的预约号，工具层也没有能力越过当前顾客和当前门店的范围。

## 第三层：业务规则必须写在工具和存储层

预约并不是把几个字段写进数据库就结束了。创建前至少要检查：

- 日期和时间是否合法，是否已经过去；
- 师傅是否属于当前门店；
- 是否在营业时间、节假日或请假时间；
- 顾客是否重复提交相同预约；
- 当前时段是否已被其他顾客占用。

这些规则如果只写在 Prompt 里，会出现两个问题。

第一，模型可能漏掉步骤。例如没有先查排班，直接创建预约。

第二，其他入口可能绕开 Agent。未来增加管理端、定时任务或新的模型时，如果业务规则只存在于某一份 Prompt 中，不同入口的行为会逐渐不一致。

所以 OpenBook 会在 Prompt 中描述正常工具流程，同时在工具层和存储层再次执行确定性校验。模型按正确顺序调用当然最好；顺序错了，服务端仍然会拒绝非法写入。

这也是我后来越来越明确的分工：

- Prompt：流程引导、参数语义和回复约束；
- 工具层：输入校验、可信身份、权限和业务规则；
- 存储层：事务、唯一约束和最终一致性；
- 模型：理解自然语言，在被允许的动作中做选择。

## 第四层：并发问题与模型无关

预约流程通常是：

1. 查询 Tony 14:00 是否空闲；
2. 用户确认；
3. 创建预约。

但“查询空闲”和“创建预约”之间存在时间窗口。两个顾客可能同时查到 14:00 空闲，然后同时提交。

无论 Prompt 写多少遍“不要重复预约”，模型都看不到另一个请求正在做什么。单个会话里的串行推理，也无法解决多顾客、多进程和多实例并发。

OpenBook 为时段获取 Redis 分布式锁，持锁后再进入 MySQL 事务检查和写入：

```go
l, err := lock.AcquireAppointmentLock(
    lockCtx,
    barber.ID,
    params.Date,
    params.Time,
)
if err != nil {
    return "", fmt.Errorf("该时段刚被别人抢了，我帮你看下一个空档")
}

appointment, err := storage.CreateAppointmentFullContext(...)
```

Redis 锁用于减少并发竞争，但它也不是最终事实来源：锁可能过期，Redis 可能不可用，进程也可能在关键时刻退出。

因此数据库还有活跃时段唯一键，保证同一门店、师傅、日期和时间只能存在一个有效预约；取消预约后释放该键。数据库冲突会统一转换为 `ErrSlotTaken`，再由工具给出顾客能理解的回复。

这是一种分层保护：

```text
排班查询：改善交互体验
        ↓
Redis 时段锁：降低并发争抢
        ↓
MySQL 事务：保证一次业务写入的完整性
        ↓
数据库唯一约束：守住最终不变量
```

其中任何一层都不是 Prompt 能替代的。

## 第五层：不能确认成功，就不能回复成功

Agent 系统还有一种很危险的错误：数据库也许成功了，也许没成功，但模型给用户生成了一句确定的“预约成功”。

例如：

- 模型调用超时，客户端不知道工具是否已经完成；
- Redis 锁在事务期间失效；
- 数据库写入返回异常，最终状态无法确认；
- 模型供应商不可用，系统切换到降级模型。

OpenBook 的创建工具在事务完成后，会重新读取预约并核对门店、状态、师傅、日期和时间。只有这些字段都与本次请求一致，才返回成功结果：

```go
persisted, err := storage.GetAppointmentContext(
    operationCtx,
    appointment.ID,
)
if err != nil ||
    persisted.ShopID != appointment.ShopID ||
    persisted.Status != "active" ||
    persisted.BarberName != params.BarberName ||
    persisted.Date != params.Date ||
    persisted.Time != params.Time {
    return "", fmt.Errorf(
        "预约结果校验失败，请勿向顾客确认成功；请稍后查询预约状态",
    )
}
```

当所有模型供应商都不可用时，系统会退化为 Stub：只回复“助手暂不可用”之类的安全信息，不调用工具、不写数据库。

这个降级看起来不够“智能”，但它比猜测业务结果更可靠。

对于会产生副作用的 Agent，我认为一个很重要的产品原则是：

> 宁可明确告诉用户“当前无法确认，请稍后查询”，也不能把不确定结果包装成成功。

## Prompt 仍然重要，只是职责不同

说“不能只靠 Prompt”，并不是说 Prompt 不重要。

在 OpenBook 中，Prompt 仍负责：

- 告诉模型预约、取消和改约的正常工具流程；
- 要求实时排班和预约状态以本轮工具结果为准；
- 限制模型不要根据历史消息猜测当前状态；
- 约束何时可以转人工；
- 把工具结果整理成简短、友好的顾客回复。

但 Prompt 不再负责证明权限、不变量和事务结果。

可以把整套系统想象成一家公司：模型是前台接待，Prompt 是工作手册，业务工具是办事窗口，服务端身份是工牌，数据库约束则是财务和门禁制度。

不能因为工作手册写了“不要越权”，就把所有后台权限交给前台。

## 我最后总结出的五条原则

如果你也在做能调用工具、修改数据的 Agent，可以先检查这五件事：

1. **最小能力面**：不需要的危险工具是否根本没有注册？
2. **可信身份**：租户、顾客和操作者身份是否来自服务端，而不是模型参数？
3. **确定性校验**：权限和业务规则是否落在工具或服务层？
4. **最终不变量**：并发和一致性是否由事务、锁和数据库约束保护？
5. **安全失败**：结果无法确认时，系统是否会拒绝写入和拒绝宣称成功？

如果其中任何一项的答案是“Prompt 里已经写了”，它很可能还不是真正的安全边界。

## 关于 OpenBook

[OpenBook](https://github.com/yuterigele/openbook) 是一个使用 Go、CloudWeGo Eino、MySQL 和 Redis 构建的美发门店微信预约 Agent MVP。

它不是生产就绪的 SaaS，也不是一个通用聊天机器人。这个项目主要用来验证：当 Agent 开始查询和修改真实业务数据时，如何处理身份隔离、工具白名单、并发撞单、幂等、事务和失败降级。

项目支持本地 Docker Compose 运行。欢迎拿下面几个场景来测试它：

- 使用另一个顾客的预约号尝试查询或取消；
- 重复发送同一条预约请求；
- 两个顾客并发抢同一个时段；
- 关闭模型或 Redis 后观察系统如何降级。

如果你跑出了越权、重复预约，或者“实际没成功却回复成功”的情况，欢迎直接提交 Issue。相比一句“欢迎 Star”，我现在更想知道这套边界还能被什么真实场景击穿。
