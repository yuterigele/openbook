# OpenBook 工程问题复盘

本文记录预约 Agent 的典型工程问题，并按“问题—方案—取舍—验证”整理可复用的设计依据与边界。

---

## 1. “明天”被解析成过去日期

### 问题

线上日志中，用户在 2026-07-22 13:38 说“今天下午都行”。模型却把相对日期解析为 `2026-07-15`，并先调用 `query_schedule` 返回了已过期时段；后续 `create_appointment` 才以“时间已经过去”拒绝。这类问题同样会影响“明天上午 10 点”等相对日期表达。

根因不是单一时区问题，而是模型缺少紧邻当前用户消息的、每轮刷新的时间锚点：本地 Web 的 `TurnLoop` 链路曾残留旧代码助手上下文，历史中的旧日期还能进一步污染判断。即使创建工具最终拒绝了过去时间，查询工具仍可能先把过去的排班误当成可约时段。

### 方案

- 每轮运行时按 `Asia/Shanghai` 生成当前日期和“明天”日期。
- 使用 system message 注入，并在历史消息之后、当前用户消息之前再次放置时间锚点；日期上下文不写入会话历史。
- 删除固定日期示例和旧代码助手提示。
- `query_schedule` 也拒绝过去日期，避免向模型返回历史可约时段。
- 创建预约工具继续校验目标时间必须在未来，防止模型判断错误后写库。

### 取舍

日期 system context 能显著降低模型误解，但不是最终正确性保证。自然语言日期仍可能有歧义，所以真正阻止错误写库的是工具层时间校验。若以后需要跨时区门店，不能继续全局写死上海时区，需要按门店配置时区。

### 验证

- 新增 `TestBuildRunMessagesUsesFreshSystemDateContext`，验证每轮第一条消息是包含当天日期的 system message。
- 新增 `TestBuildTodayContextAt_UsesShanghaiCalendar`，以 2026-07-22 13:38 验证“今天/明天/后天”分别是 07-22、07-23、07-24。
- 新增 `TestQuerySchedule_RejectsPastDate`，验证查询排班阶段就拒绝过去日期。
- 验证上下文不再包含旧 filesystem/code-assistant 指令。
- 手工新建会话测试“今天下午都行”和“明天上午 10 点”，检查工具参数分别落在当天未来时段和真实次日。

## 2. 容器启动后没有默认理发师和服务

### 问题

Docker 启动成功，但 Agent 查询时返回“本店没有可预约师傅”。最初看起来像模型或工具问题，实际是种子数据没有正确初始化。

根因是数据库迁移完成后执行 `SeedDefaultData`，但全局数据库句柄尚未赋值；种子逻辑访问了未就绪的连接，因此默认门店、Tony、Kevin 和服务项目不完整。

### 方案

调整初始化顺序：数据库连接和迁移成功后，先设置可供仓储层使用的数据库句柄，再执行默认数据 Seed。

### 取舍

保留自动 Seed 有利于本地 Demo 一键启动，但生产环境不能无条件写演示数据。Demo Seed 必须幂等，并与生产迁移/初始化策略区分。

### 验证

- 新增 `storage/seed_test.go`。
- 验证默认门店、理发师、服务和后台账号均被创建。
- 重复运行 Seed，确认不会生成重复数据。
- 容器启动后直接查询 MySQL 并实际调用 `list_barbers`、`list_services`。

## 3. 用户猜到预约号后可能取消他人预约

### 问题

早期 `get_appointment` 和取消逻辑主要按预约 ID 操作。若预约号被猜到、截图泄露或用户主动要求取消他人预约，仅靠 Prompt 说“只能操作自己的”并不能形成授权边界。

### 方案

- `shop_id`、`open_id`、`external_user_id` 只由企业微信回调或本地服务端会话注入 context。
- 模型只允许提供预约号和取消原因，不能决定门店或顾客身份。
- 工具先把消息身份映射为真实顾客，再按 `appointment_id + shop_id + customer_id` 查询。
- 取消在事务中使用同样的范围条件读取和更新，避免先查后改的竞态。
- 不匹配时统一回复“找不到属于您的预约”，不泄露预约是否存在或属于谁。

### 取舍

统一错误会降低一点排障便利性，但能防止存在性和归属信息泄露。管理员取消与顾客取消应走不同授权入口，不能为了复用代码放宽顾客工具权限。

### 验证

- `TestGetAppointment_RejectsOtherCustomer`。
- `TestCancelAppointmentTool_RejectsOtherCustomer`。
- 正常顾客查询/取消仍成功，攻击者使用同一个预约 ID 必须失败。

## 4. 顾客输入可以诱导 Agent 执行文件或 Shell 操作

### 问题

早期 Agent 使用的预构建后端会自动注册文件读写、搜索和 Shell 执行能力，文件型 RAG 也允许读取路径。预约顾客虽然业务上不需要这些能力，但提示注入可能让模型调用它们，形成真实副作用。

### 方案

- 从顾客 Agent 移除本地 backend、Streaming Shell 和文件路径读取工具。
- 关闭通用子 Agent，只注册预约白名单工具。
- 顾客不能调用标记完成、标记爽约等店员能力。
- 工具层继续做身份、范围和参数校验，不把 Prompt 当权限系统。

### 取舍

移除通用工具后，Agent 的“通用能力”变弱，但预约场景根本不需要这些能力。最小能力面比“功能越多越好”更适合会产生业务副作用的 Agent。

### 验证

- 检查 `internal/agent/agent.go` 的工具白名单。
- Agent 配置不再包含本地 backend 或 Shell。
- 输入 Linux 命令时不出现文件、Shell、SQL 工具调用。
- `go test ./internal/agent ./server` 验证配置与提示词约束。

## 5. Linux 命令和越权请求被错误转人工

### 问题

用户先尝试取消不属于自己的预约，再发送 `rm -rf all`。模型把“无法处理”理解为兜底场景，调用 `handoff_to_human`，给门店制造了无效人工工单。

### 方案

- 删除“连续未知意图自动转人工”的宽泛规则。
- 在所有消息入口、调用 Agent 前增加确定性的“输入相关性/风险”阈值：预约关键词、问候和问句加分；提示注入、命令、外链引流、重复乱码扣分；分数不超过 -2 时直接回复预约范围说明，不进入 Agent 或业务工具。
- 只允许明确要求人工，或投诉、退款、改价等真实业务超出能力时转人工。
- 命令、文件/数据库操作、越权预约直接拒绝。
- `handoff_to_human` 工具要求带原始用户消息，并在工具层识别明显命令和越权请求；即使模型误调用也不写工单。

### 取舍

规则匹配无法覆盖所有攻击表达，因此它不是完整安全授权；真正的安全来自危险工具不存在、业务工具有归属校验。该阈值刻意放得保守：短问候和不完整预约请求会放行，避免把正常顾客误伤；它主要防止垃圾流量、无关长文本和错误升级。

### 验证

- `TestHandoffToHuman_RejectsCommandAndUnauthorizedRequests`。
- `TestAssessUserInputTrust` 覆盖问候、预约、提示注入、命令、乱码和长无关文本；`TestProcessAgentMessage_UntrustedInputSkipsAgent` 验证低分消息不会调用 Agent。
- 验证命令和他人预约请求不会写入 `handoff_to_human` 事件。
- 明确“我要投诉、叫店长来”仍能正常创建人工记录。

## 6. 同一时段并发创建导致撞单

### 问题

“先查排班再创建”之间存在时间窗口。两个请求可能同时看到 10:00 空闲，并同时尝试写入。模型层串行对话不能解决多顾客、多实例并发。

### 方案

- 工具层按 `barber_id + date + time` 获取 Redis 分布式锁。
- 持锁后在 MySQL 事务中重新检查时段占用，再创建预约和顾客档案。
- 冲突统一转为 `ErrSlotTaken`，由 Agent 翻译成“这个时段刚被预约，请换一个时段”。

### 取舍

Redis 锁降低并发冲突，但锁可能过期、Redis 可能不可用，不能被当成最终事实来源。当前代码还有一个应明确说明的生产化边界：预约表尚未用复合唯一索引把时段唯一性固化到数据库，若进入真实高并发试点，应补 `(shop_id, barber_id, date, time)` 唯一约束作为最终兜底。

### 验证

- 并发发送相同时段创建请求，只允许一个成功。
- 验证锁释放、超时和冲突错误路径。
- 验证失败请求不残留半完成顾客或预约记录。
- 真实试点前新增数据库唯一约束及对应并发测试。

## 7. 企业微信客服回调可能重复处理消息

### 问题

微信客服消息通过 cursor 拉取，回调可能重复触发，服务重启后内存去重状态也会丢失。如果重复处理“帮我预约”，可能重复调用模型、重复写库或重复回复。

### 方案

- 将客服同步 cursor 持久化到数据库。
- 使用企业微信 `msgid` 作为去重键，写入 `kf_seen_msg`。
- 过滤非顾客文本和时间窗口外消息。
- 同一会话短时间连续消息做 debounce 合并，避免多条碎片消息触发多次 Agent 推理。

### 取舍

当前去重标记与完整业务处理不是一个跨系统原子事务：过早标 seen 可能在后续失败时丢消息，过晚标记则可能重复。更严格的方案可以引入 inbox/outbox 状态机和可重试消费，但对本地 MVP 成本较高。

### 验证

- `storage/kf_sync_state_test.go` 验证 cursor 与 msgid 持久化。
- `server/handle_kf_callback_test.go` 验证重启后不重复处理历史消息。
- `server/kf_debounce_test.go` 验证同一用户连续消息合并，多个用户互不影响。

## 8. 工具返回真实结果，但模型最终回复说错师傅或日期

### 问题

项目中出现过模型凭上下文印象编造师傅请假时间、推荐仍在节假日清单中的日期，或工具返回 Kevin 后最终回复仍沿用用户最初说的其他师傅。历史中的旧错误还可能继续污染下一轮。

### 方案

- 排班、请假、服务价格、节假日等具体事实每轮重新调用工具。
- 师傅昵称先通过 `list_barbers` 映射为本店真实名称。
- 改约前调用 `get_appointment` 获取当前真实师傅和状态。
- Prompt 明确历史具体陈述不算事实，最终回复必须使用本轮工具结果。
- 对预约创建成功结果，保留预约 ID、师傅、日期、时间和服务作为后续校验依据。

### 取舍

这些 Prompt 与流程约束主要降低概率，不是完全强保证。更强的生产方案是：工具成功后由服务端模板生成交易确认文案，或发送前将回复中的关键字段与结构化工具结果比对；这样会牺牲部分语言自由度，但适合预约、支付等高风险操作。

### 验证

- `internal/agent/agent_prompt_test.go` 固化关键事实必须来自工具、历史不算事实等约束。
- 用反例测试工具返回 Kevin、用户原话为其他昵称时，最终回复不得错报。
- 检查节假日推荐前是否调用完整假期清单和排班工具。

## 9. 所有 LLM Provider 初始化失败时服务无法启动

### 问题

DeepSeek、OpenAI 兼容接口或 Ark 可能因为密钥、网络或服务异常无法初始化。如果 Agent 直接依赖单个模型，模型故障会让整个 HTTP 服务启动失败；但错误降级又可能在未确认业务结果时写库。

### 方案

- 按配置构建 DeepSeek → OpenAI 兼容协议 → Ark 的降级链。
- 记录每个 provider 的初始化结果、错误和延迟。
- 所有真实模型都失败时返回 chat-only stub，让服务和后台仍可启动。
- Stub 不调用业务工具、不写预约，只返回能力受限的友好提示。

### 取舍

服务“能启动”不代表预约能力可用。降级必须是安全降级，不能用规则猜测“预约成功”。监控需要区分 HTTP 健康、模型可用和业务可写三个层级，否则健康检查会掩盖核心能力不可用。

### 验证

- `TestNewModelWithFallback_AllProvidersFail_ReturnsStub`。
- Agentic 消息类型也有对应 fallback 测试。
- 验证 stub 不产生 tool call、不写库。
- 验证 provider 链的失败信息可从日志或指标观察。

## 10. 当前是否应该引入向量库

### 问题

Agent 项目很容易为了展示技术栈而直接加入向量库，但 OpenBook 当前核心问题是实时预约：师傅、服务、档期和预约状态都是结构化、频繁变化并要求强一致的数据。

### 方案

- 预约核心数据继续使用受约束业务工具查询 MySQL。
- RAG Workflow 只作为独立实验，不加入预约交易主链路。
- 只有当多商家积累大量服务说明、活动规则、售后政策，且离线评测证明结构化查询或关键词方案不足时，才引入带 `shop_id` 强制过滤的混合检索。

### 取舍

暂不上向量库减少了 embedding、切块、索引更新、租户隔离和召回评测成本，也避免旧活动被召回。但非结构化问答能力会受限，因此要用真实门店问题分布决定，而不是永久拒绝 RAG。

### 验证

- 收集真实门店问答，区分结构化预约问题和非结构化知识问题比例。
- 当引入 RAG 时建立标注集，评估 Recall@K、MRR、答案正确率、引用命中率、延迟和成本。
- 删除/更新文档后验证旧 chunk 不再召回。
- 服务端从可信 context 注入 `shop_id`，检索层强制过滤，不能让模型选择租户。

## 通用复盘模板

记录或评审类似问题时，可按以下五项组织：

1. **问题**：当时出现了什么现象，真正风险是什么。
2. **可信来源**：哪些数据可信，哪些来自用户或模型不能信。
3. **方案**：分别在哪一层处理，最终事实由谁保证。
4. **取舍**：这个方案解决了什么，还有什么明确边界。
5. **验证**：用什么测试、日志、指标或复现步骤证明修复有效。

先记录具体现象和风险，再解释设计原因、边界和验证证据，避免只罗列框架或结论。
