# 旧预约迁移规划

OpenBook 保留旧的 `appointments` 表，并通过迁移期适配器逐步切换到通用 `Booking`、`Allocation` 和 `Outbox` 记录。当前实现提供的是只读规划器，不是生产数据迁移命令：它不会连接或修改数据库。

## 当前规划器

`storage.PlanLegacyAppointmentMigration` 接受旧预约、旧服务目录、旧员工目录和显式迁移上下文，返回带版本号的规划报告：

- `MerchantID` 必须由部署方显式提供；不会把旧 `ShopID` 猜成商户 ID。
- `ShopID` 映射为 `LocationID`，可用 `LocationID` 选定单个门店。
- 服务按同一门店内的名称匹配，找不到或匹配多条都会阻断。
- 员工按同一门店内的 `BarberID` 匹配，并校验员工归属。
- 空顾客 ID、无效日期时间、目标 ID/幂等键碰撞和不支持的旧状态都会阻断。
- `active` 映射为 `confirmed`，`cancelled` 映射为 `cancelled`，`completed` 映射为 `completed`；`noshow` 等状态不自动猜测。
- 旧记录之间或与已存在的 next 预约发生员工/资源冲突时，冲突两边全部阻断，不按输入顺序选择赢家。
- 旧表没有资源占用字段，因此只生成员工 `Allocation`，不会伪造或推断 `ResourceID`；报告会保留这一限制。

每一行报告都保留 `legacy_appointment_id`、确定性的 `booking_id` 和 `idempotency_key`。`state=ready` 只是表示规划校验通过，不代表已经写入数据库；后续执行器只能消费 ready 行，并必须在落库前再次校验报告版本和目标状态。

## 迁移窗口要求

真实迁移执行前必须针对单个商户建立维护窗口和单写者边界：

1. 停止旧预约写路径，等待 Agent、消息 Worker 和数据库事务完成。
2. 读取切换水位和 next 表现状，生成并保存完整规划报告。
3. `blocked` 必须为 0，且记录数量、ID 映射、归属、状态、时间区间和占用关系通过人工复核；不能忽略阻断项继续迁移。
4. 在明确的版本化事务执行器中写入 Booking、Allocation、Outbox 及映射审计记录，并在提交后复核数量和租户范围。
5. 原子切换写后端和 Schema 版本，恢复消息消费；观察期内新写只进入 next。

应用镜像回滚不会自动逆向数据库迁移。新写路径已经产生数据后，不能只切回旧开关；必须使用经过验证的反向迁移或恢复备份，并接受窗口内数据补录。迁移报告和备份应与发布版本一起留存，供取消、改约、消息重放和故障对账使用。
