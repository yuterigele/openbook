# 美发店智能预约助手 · 产品需求文档

## 1. 定位与范围

OpenBook 是接入企业微信的美业预约助手。顾客通过自然语言查询档期、创建、改约或取消预约；门店通过后台管理师傅、服务、营业时间与预约状态。

目标客户是 1–5 名师傅的小型美发门店。首期只解决预约闭环，不做收银、库存、营销自动化或通用 Agent 平台。

## 2. 用户与目标

| 角色 | 目标 |
|---|---|
| 顾客 | 不打电话，在微信中完成预约或取消 |
| 店主 / 店员 | 减少手工登记、撞单和漏单 |
| 平台运营 | 在不越权的前提下稳定运营多门店服务 |

成功标准：

- 顾客能在一次对话中完成已知时间、师傅和服务的预约；
- 不会产生同一师傅同一时段的有效重复预约；
- 顾客只能查看、取消或改约自己的预约；
- 模型或外部输入不具备文件、Shell、任意 SQL 或后台管理权限。

## 3. 核心功能

### 3.1 顾客预约

1. 顾客询问师傅、服务或可预约时段。
2. Agent 解析意图；涉及档期时必须调用业务工具查询实时数据。
3. 顾客确认服务、师傅和时间后创建预约。
4. 创建成功后回复预约号、时间、师傅与服务；失败时说明可选时段或下一步。

创建预约必须校验：

- 门店、师傅、服务均存在且可用；
- 时间符合门店营业时间、请假和节假日规则；
- 顾客身份来自服务端上下文；
- 时段未被占用。

### 3.2 查询与改约

- 查询档期时展示可预约时段、请假或已约满的必要信息，不泄露其他顾客信息。
- 改约前必须重新读取当前预约，避免使用会话历史中的过期师傅或时间。
- 改约按“新建时段校验成功后再释放旧时段”的业务事务处理；失败时原预约保持不变。

### 3.3 取消预约与违约

- 取消工具只接受预约标识等业务参数，门店与顾客身份由服务端注入。
- 未找到、无权访问或已取消时，统一返回不泄露资源存在性的提示。
- 取消结果记录取消来源、原因与时间，用于审计和后续违约统计。
- 晚取消、爽约和黑名单规则由确定性服务端代码执行，不能由模型自行判断或修改。

### 3.4 师傅请假

- 商户可创建、撤销和查看请假记录。
- 请假期间不可新建预约；查询结果需明确区分请假与普通已约满。
- 请假影响已有预约时，系统按配置执行取消或改派，并保留通知和审计记录。
- 已取消或过期的请假不应继续影响可预约时段。

### 3.5 转人工

仅在以下情形允许转人工：

1. 顾客明确要求人工服务；
2. 投诉、退款、改价等超出预约工具权限的请求；
3. 连续多轮无法识别需求。

转人工需按会话或消息引用去重。命令注入、无关内容和越权请求直接礼貌拒绝，不创建人工工单。

## 4. 商户后台

商户后台按登录身份限制到所属门店，至少支持：

- 师傅、服务、营业时间、午休和节假日管理；
- 预约列表与状态更新；
- 顾客与标签的查询和管理；
- 请假、转人工待处理和基础经营看板；
- 订阅状态与通知记录查询。

连锁场景可提供跨店聚合视图，但单店数据读取和写入始终以 `shop_id` 为隔离边界。

## 5. 业务规则与安全边界

### 5.1 可信身份

`shop_id`、顾客身份、会话身份和后台操作者身份只能由企业微信回调、认证中间件或服务端路由注入。模型参数、HTTP body 和会话文本中的同名字段均不可信。

### 5.2 工具调用

- Agent 仅能调用显式注册的预约工具；
- 模型负责理解自然语言和选择工具，不负责授权、时间精算、并发控制或状态一致性；
- 工具返回失败时，不得向顾客声称操作成功；
- 工具调用与关键状态变更应记录可追踪的审计信息。

### 5.3 多租户与隐私

- 每次资源查询、修改和管理操作都校验门店范围；
- 顾客操作额外校验预约归属；
- 不向顾客暴露其他顾客姓名、预约号、联系方式或请假敏感原因；
- 后台角色权限由服务端执行，前端隐藏不构成授权。

### 5.4 并发与幂等

- 创建和改约使用分布式锁降低并发冲突；
- 数据库事务与唯一约束是预约时段一致性的最终保障；
- 消息回调按消息 ID 去重；
- 对可能重复投递的写操作使用幂等键或基于业务状态的去重。

### 5.5 时间规则

- 业务时间统一使用 `Asia/Shanghai`；
- 相对日期由服务端提供当前时间基准，并在写入前转为绝对日期时间；
- 预约、请假、营业时间和取消政策使用同一时间语义。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| 可用性 | 模型暂时不可用时安全降级，不写入不确定结果 |
| 性能 | 查询与工具调用设置超时、限流和有界并发，避免突发流量耗尽资源 |
| 可观测性 | 记录请求链路、模型 provider、工具调用、重试、锁冲突和业务结果 |
| 通知 | 通知失败可重试并可追踪；通知成功不是预约写入成功的依据 |
| 数据保留 | 预约取消、改派、请假和人工转接保留审计记录，不以缓存 TTL 删除业务事实 |

## 7. 验收标准

### 7.1 预约主链路

- 给定有效门店、顾客、师傅、服务和空闲时段，创建一次预约并返回准确结果；
- 两个并发请求争抢同一师傅、同一时段时，最多一个成功；
- 节假日、营业外、请假和已占用时段均不能创建成功；
- 重复消息不会创建多条预约。

### 7.2 授权与安全

- 顾客取消他人预约时，不泄露该预约归属或存在性；
- 模型伪造 `shop_id`、`customer_id` 或后台身份时不影响服务端授权结果；
- 提示注入不能获得未注册工具、Shell、文件系统或任意数据库能力；
- 不符合条件的转人工调用不产生事件或工单。

### 7.3 降级与异常

- 模型、Redis、通知或外部接口失败时，回复与实际业务状态一致；
- 无法确认写操作结果时，不自动宣称成功；
- 模型重试不会造成重复预约、取消或重复通知。

## 8. 非目标

- 不做美团式流量平台；
- 不做完整收银、库存或营销 SaaS；
- 不将 RAG 用作预约、取消、改约等交易操作的事实来源；
- 不依赖 Prompt 代替权限、数据校验或并发保护。
